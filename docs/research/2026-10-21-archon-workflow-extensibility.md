# Archon workflow extensibility: contributing to a workflow you do not own, 2026-10-21

Research for [Practice Packs must stack](https://github.com/unic/unic-agents-plugins/issues/520), under the map [#373](https://github.com/unic/unic-agents-plugins/issues/373).

Researched 2026-10-21. Question: how independently installable Practice Packs can contribute steps, prompts, skills, MCP servers or context to `unic-dlc-*` workflow runs in a Consumer repository, when one plugin owns and installs those YAML files verbatim.

## 2. Templating and interpolation in node fields

**Prompt-text substitution exists. Structural fields take literals only.**

Prompt-text surfaces (**documented**, `docs/reference/variables.md`, "Workflow Variables"):

- Substituted in `command:` file bodies, `prompt:`, `bash:`, `script:`, `loop:`, `loop_group:`, and a `workflow:` node's `input:`.
- Also in AI-configuration text: `systemPrompt:` and `agents.<id>.prompt` / `agents.<id>.description`.
- Sources: engine variables (`$ARGUMENTS`, `$USER_MESSAGE`, `$WORKFLOW_ID`, `$ARTIFACTS_DIR`, `$TYPED_ARTIFACTS_FILE`, `$STATE_DIR`, `$BASE_BRANCH`, `$DOCS_DIR`, `$CONTEXT` and aliases, loop variables), node outputs `$nodeId.output[.a.b]`, and `$INPUTS.<name>` from a workflow's `inputs:` or an `include:`/`workflow:` node's `with:`.
- Config feeds two of them: `$DOCS_DIR` from `docs.path` and `$BASE_BRANCH` from `worktree.baseBranch` in `.archon/config.yaml`.
- No `$ENV_VAR` substitution in prompt text (**not found** in `variables.md`). In `bash:`/`script:` nodes, user-controlled values and `INPUTS_*` arrive as process environment variables, not spliced text. Variables from `.archon/.env`, `~/.archon/.env` or `config.yaml`'s `env:` section reach `bash:`/`script:` through the process environment (**documented**, 0.12.0 changelog, #3509, #3514).
- `include:` `with:` values are inserted verbatim at load time and are never expressions (**documented**, `docs/guides/authoring-workflows.md`, "Passing values into an included block").

Structural fields (**source**, v0.12.1):

- `skills`, `plugins` and `allowed_tools` pass straight from the parsed node to the provider: `packages/workflows/src/dag-executor.ts`, around lines 2125-2131 (`skills: node.skills`, `plugins: node.plugins`, `allowed_tools: node.allowed_tools`). Every `substituteWorkflowVariables` call in that file targets prompt, script or input text, none of these fields.
- The `skills` schema is `z.array(z.string().min(1))` (`packages/workflows/src/schemas/dag-node.ts:228`).
- `mcp:` is a literal path or `{ path, optional }`. Relative paths resolve against the run's checkout; only home-scoped workflows fall back to the YAML's own directory (**documented**, `docs/guides/mcp-servers.md`, lines 95-100). Inside the MCP JSON file, only `env` and `headers` values expand `$VAR`/`${VAR}` from Archon's process environment; `command`, `args` and `url` are untouched (**documented**, same file, "Environment Variable Expansion"). Whether `config.yaml` `env:` entries feed that expansion: **needs measurement**.
- `include:` takes a literal workflow name, "no `include: $something`" (**documented**, "Non-goals (Phase 1)").
- `model:` has an indirection layer: tiers (`large`/`medium`/`small`) and aliases (`@name`) defined in `.archon/config.yaml` or a per-run `--config` file (**documented**, `docs/reference/configuration.md`). This is the only structural field with a config-driven indirection. Nothing equivalent exists for skills or MCP.

## 3. Composition and override mechanisms

| Mechanism                                            | Exists                   | Notes                                                                                                                                                                                                                                                                                                                                                                                 | Evidence                                                                                                                                                                                     |
| ---------------------------------------------------- | ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `include: <workflow-name>`                           | Yes, since before 0.10.1 | Inlines another workflow's nodes at load time as `<includeId>__<nodeId>`. Target resolves **by `name:`** with precedence bundled < `~/.archon/workflows/` < repo `.archon/workflows/`. `with:` passes values to `$INPUTS.<name>`. Nesting up to 3 levels, cycle-checked. A missing target is a load error that drops the includer                                                     | documented (`authoring-workflows.md` "Composing Another Workflow with `include:`"); source (`include-expander.ts:1318`, "include target '…' not found"); measured on 0.10.1                  |
| `workflow: <name>` child run                         | Yes                      | Separate governed run at execution time, its own record, gates, artifacts and cost. `input:` or `with:`                                                                                                                                                                                                                                                                               | documented ("Launching a Separate Governed Run")                                                                                                                                             |
| Extending a base workflow, overriding one named node | No                       | A composer contributes ordering and gates; it "does not reach inside". No deep access to an included block's nodes                                                                                                                                                                                                                                                                    | documented ("No deep access"); not found in schema                                                                                                                                           |
| Optional or conditional include target               | No                       | `when:` on an include node gates the block's entry nodes at runtime, but the target must still exist at load                                                                                                                                                                                                                                                                          | source; documented                                                                                                                                                                           |
| Named command files                                  | Yes                      | `command: <name>` in a legacy (flat) workflow resolves at runtime: repo `.archon/commands/` → `commands.folder` from `.archon/config.yaml` → `~/.archon/commands/` → bundled. First match wins. Duplicate basenames inside one scope are a user error. Packaged workflows (`.archon/workflows/<pack>/<workflow>/`) resolve commands only from their own `commands/`, with no fallback | source (`executor-shared.ts` `loadCommandPrompt`, `paths/src/archon-paths.ts:362`, same order at v0.10.1); documented (`global-workflows.md`, `configuration.md` "Command Folder Detection") |
| Workflow packs (`archon plugin add`)                 | Since 0.11.0             | See Q6                                                                                                                                                                                                                                                                                                                                                                                | documented                                                                                                                                                                                   |

Two consequences for Practice Packs:

1. **An include slot is shadowable, but holds one occupant.** If a `unic-dlc-*` Box contains `include: practice-hook`, whichever single file supplies `name: practice-hook` at the highest scope is inlined. Measured on 0.10.1: a home stub (`~/.archon/workflows/practice-hook.yaml`, one node) ran when alone; a project file with the **same filename** replaced it (both project nodes ran, the home stub did not).
2. **Two contributors cannot share a slot.** Measured on 0.10.1: a project file `acme-practice.yaml` declaring `name: practice-hook` next to the home `practice-hook.yaml` produced `Duplicate workflow name 'practice-hook' … same-name files do not override each other (overrides are by filename)`. Both files were dropped, and the includer then failed to load with `include target 'practice-hook' not found`. A Pack that picks a colliding `name:` disables the Box that includes it.

## 4. Discovery precedence and shadowing

Documented (`docs/guides/global-workflows.md`, "Load Priority"; `docs/reference/configuration.md`, line 33):

1. Bundled (lowest).
2. Home: `~/.archon/workflows/`, `~/.archon/commands/`, `~/.archon/scripts/` (or `$ARCHON_HOME/…`).
3. Repo: `<repoRoot>/.archon/workflows/`, `.archon/commands/`, `.archon/scripts/` (highest).

Details from source (`packages/workflows/src/workflow-discovery.ts`, header comment lines 10-21 and discovery around lines 1295-1385):

- **Workflows override by filename** (basename, e.g. `unic-dlc-build.yaml`), not by `name:`. Two surviving files with the same `name:` but different filenames are both dropped with a duplicate-name error (lines 911-940). Measured on 0.10.1, see Q3.
- Packaged layouts: a filename collision across packaged folders inside one scope drops both (lines 470-490).
- Commands: first match in repo → `commands.folder` → home → bundled (Q3).
- Installed packs sit outside this precedence. A project or global workflow whose `name:` equals an installed qualified name is not loaded ("that name belongs to an installed plugin"), so no project or global file can shadow an installed workflow (lines 1170-1186; test `installed-packs.test.ts`, "a project workflow cannot shadow an installed name").

For the `unic-dlc-*` Boxes: `unic-archon-dlc`'s `/setup` installs them into the Consumer's repo `.archon/workflows/` (`apps/claude-code/unic-archon-dlc/commands/setup.md:217`), which is the highest legacy scope. So:

- A home-scope file cannot shadow a Box.
- A Consumer-local file with the same basename is the same path, so writing it overwrites the Box.
- A Consumer-local file with a different basename and the same `name:` drops **both** (duplicate-name error).
- A Box's command files, if it used named `command:` references in flat layout, could be shadowed by a repo `.archon/commands/<name>.md`. The current Boxes use inline prompts.

## 5. Project-level defaults for node skills or MCP; `skills: all`

**Not found.** No project, repo or workflow-level default for `skills:`, `mcp:` or `plugins:` exists at v0.12.1.

- The workflow-level schema (`packages/workflows/src/schemas/workflow.ts`, lines 200-286) has `provider`, `model`, `effort`, `fallbackModel`, `betas`, `sandbox`, `worktree`, `container`, `budget`, `inputs`, `returns` and similar, but no `skills`, `mcp` or `plugins` (**source**). The docs list workflow-level defaults only for `effort`, `fallbackModel`, `betas`, `sandbox` (**documented**, `authoring-workflows.md`, "Workflow-level defaults").
- `.archon/config.yaml` offers `assistants.claude.settingSources` (eligibility of `project`/`user` sources), not activation. "In workflow nodes, discovery does not activate ambient skills: the node's `skills:` list remains the exact active set, and omission/`[]` selects none" (**documented**, `configuration.md`, "Claude settingSources").
- **`skills: all` is not fixed.** The Claude provider sets `options.skills = nodeConfig.skills ?? []` (`packages/providers/src/claude/provider.ts:651`, same at v0.10.1 line 511), and the schema accepts only a string array (**source**). The skills guide calls the per-node list "an exact allowlist" (**documented**, `docs/guides/skills.md`).
- Unknown skill names still warn and are ignored: "Absent from every skills directory → Warning, and the run continues", because built-in and `plugin:skill` names live outside skill directories. A name installed only outside an enabled `.claude/skills/` root is now an **error before spend** (**documented**, `skills.md`, "How Claude handles an unresolved name"; **source**, `provider.ts` lines 661-710).

1. On 0.12.x: whether a `SessionStart` native hook in project `.claude/settings.json` injects `additionalContext` into an Archon Claude node.
2. On 0.12.x: whether `.claude/rules/*.md` load into a node under `settingSources: ['project']`.

## Repo facts this research contradicts

- `.claude/rules/learned.md` (2026-10-01) says "By default a node also loads user-scope plugins". True on 0.10.1. False from **0.12.0**: Claude nodes load no installed Claude Code plugins unless the node names them in `plugins:`, and they fail if one loads unnamed (0.12.0 changelog, #3574, #3578).
- `docs/guides/skills.md` at v0.12.1 confirms the 0.10.1 measurement that an unknown skill name warns and is ignored, and adds an error case for a skill found only outside an enabled `.claude/skills/` root.
