# AGENTS.md — unic-archon-dlc

Guidance for any AI agent working inside this Plugin directory. `CLAUDE.md` in this directory is a symlink to this file.

## What this Plugin is

`unic-archon-dlc` is a Claude Code Plugin in the [`unic-agents-plugins`](../../../AGENTS.md) monorepo. It scaffolds a **Harness** for the **SDLC** (the software development lifecycle; "AI development lifecycle" is this Plugin's gloss for it, never a second concept — see [`CONTEXT.md`](CONTEXT.md)): it owns the _what_ (the box set — main line `/specs` → `/tickets` → `/build` → `/pr-review` → `/qa`; on-ramps `/triage` + `/qa` findings; off-line `/setup`, `/explore`, `/improve-architecture`, `/cleanup`, `/archon-upgrade`; + `/handoff` — Matt's, referenced) and **composes the team's system-skills for the _how_** (tracker/docs/design access). Each box's **container follows its structural need** — Archon workflows for the AFK-isolated legs (`/build`, `/qa`, `/pr-review`, `/explore`), Claude Code commands/skills for the interactive/repo-global ones (the rest, composing Matt Pocock's skills rather than reimplementing them). Configuration is via the `/unic-archon-dlc:setup` slash command. See [ADR-0016](docs/adr/0016-dlc-thin-process-layer.md)–[ADR-0018](docs/adr/0018-generic-core-config-compose.md) for the two-axis architecture, [ADR-0014](docs/adr/0014-workflow-per-box-decomposition.md) for the box set, [ADR-0030](docs/adr/0030-harness-hosts-methods.md)–[ADR-0032](docs/adr/0032-box-method-vocabulary.md) for the Harness/Method division, and [`CONTEXT.md`](CONTEXT.md) for the vocabulary.

## Plugin doctrines

Load-bearing invariants. These either originate in a Plugin ADR or are policy decisions that are not obvious from the code.

- **Setup is the installer and the sole configuration entry point, and ownership decides what a re-run does.** The `/unic-archon-dlc:setup` slash command lands six things in a Consumer: the Boxes, the Methods, `.archon/unic-dlc.config.yaml`, the tracker contract, the `CLAUDE.md` block, and the formatter exclusions that keep this project's own toolchain off the two installed trees. It conducts the conversation and **composes the team's system-skills** to detect their stack, all with its own tools. **Three treatments, decided by who owns the artefact**: a tree this Plugin owns is **replaced** on every run; a tenant-owned file is written on the first run and thereafter **reported** on, changing nothing; a marked block inside a tenant-owned file is **patched** in place, with everything outside the markers preserved verbatim. `reconfigure` is the one override that rewrites a tenant-owned file, offered per file after showing what would change. Two rules that follow, both easy to get backwards: an upgrade needs no argument, because the step that installs both trees runs before the conversation and needs no answers; and `/setup` locates its own installed directory from Claude Code's `~/.claude/plugins/installed_plugins.json` — never by searching the version cache, which holds one directory per version ever installed. See [ADR-0019](docs/adr/0019-conversational-setup.md) (supersedes [ADR-0001](docs/adr/0001-setup-as-slash-command.md)) and [ADR-0036](docs/adr/0036-setup-owns-a-named-install-set.md), both amended 2026-08-25.
- **A Consumer's formatter is what forks an installed file, so `/setup` excludes what it installs — by reading the project, never from a list of tools.** One `pnpm format` on `DXP-DesignSystem` rewrote **thirteen** Method files, because a Markdown glob reached `.archon/methods/` and nothing excluded it (2026-08-18). The failure is silent: a reflowed file raises no error and no test failure, it just stops matching the release it was copied from — and the generated header is then the only provenance a Consumer has. So `/setup` reads whatever this project runs to format or lint, whatever the language, works out each tool's exclusion mechanism from that tool's own documentation, and excludes both installed trees plus every file whose name carries `.generated.`. **Name no tool and no config filename in this Plugin's prose**: knowing that an installed file must not be reformatted is ours, and knowing which tool would do it is the project's. The Boxes are `.yaml` and that day's glob missed them by luck, so they are excluded too — the exclusion is written for the glob that grows. Where a tool's exclusion mechanism cannot carry a comment marker, `/setup` prints the entry the operator must add and reports it as an open item rather than editing a value it could not later tell from a hand-written one.
- **The DLC owns the _what_; it composes team system-skills for the _how_.** No box hardcodes a tracker/docs/design system. For docs and design it reads `.archon/unic-dlc.config.yaml` and composes the configured skill/CLI/MCP (MCP-first, CLI-fallback); for the **tracker** it reads the contract at `docs/agents/issue-tracker.md`, which names the server and the repository. See [ADR-0016](docs/adr/0016-dlc-thin-process-layer.md).
- **The Plugin is a Harness; the Methods it hosts own procedure.** The Harness owns isolation, gates, config, red/green integrity, system-skill composition, artefact durability and posting. A **Method** — Matt Pocock's skill text — owns _how_ the work is done, and no Box paraphrases, summarises or improves it: any paragraph in a `commands/*.md` file explaining how to do the work is a defect, because the Method already says it and the two will diverge. A Box therefore survives **only for what no Method can supply** — the structural bar that replaces ADR-0021's "adds value" judgement. Config carries _parameters_ (which, where, whether); a Method carries _procedure_, so a team wanting different method text forks the Method rather than gaining a config key. Vocabulary in [`CONTEXT.md`](CONTEXT.md); rationale in [ADR-0030](docs/adr/0030-harness-hosts-methods.md) and [ADR-0032](docs/adr/0032-box-method-vocabulary.md).
- **One dependency list, and it is prose.** The table under [README.md § Dependencies](README.md#dependencies) is the only place a Method name sits beside the Box that reads it. Nothing generates it and nothing checks it, so edit it in the same commit as the Box or command whose Methods changed. **Never restate the list** — not here, not in a command file. A Box's own prose may name the Methods _it_ reads, but only names the table agrees with; the roll-up of what the Plugin depends on exists once. Three surfaces once said 7, 6 and 11, which is how the upstream v1.1.0 rename wave broke `/specs` and `/tickets` with CI green — the fix then was a manifest and a drift test, and the fix now is fewer surfaces: one table, no mirrors. **A rename wave is found by running a Box against a live Consumer**, which is where both 0.22.0 command defects were found; nothing in this repository can see upstream. Every Box and every command reads a Method at the literal path `.archon/methods/<name>/SKILL.md` — one path, no resolution order, no tier line, and no config or `.local` override (#381 retired both). `/qa` reads no Method: upstream deprecated `qa` at v1.1.0, so its brief shape is inlined and this Harness owns it. Methods ship in the Bundle at `vendor/mattpocock-skills/`, are installed by `/setup` into `.archon/methods/`, and are **read by path, never registered as skills** — registering them would give a Consumer running Matt's own plugin every skill twice. The plugin version is the pin; there is no `skills.pin` key. See [ADR-0031](docs/adr/0031-methods-bundled-three-tier-resolution.md), amended.
- **A Box states WHICH repository and never HOW; it stages named paths and never sweeps.** Two rules, both written **inline in every prompt that needs them** — a Box node is self-contained and imports nothing from the Plugin ([ADR-0023](docs/adr/0023-build-generic-red-green-refactor-loop.md) §5), so a rule that lives only here is invisible at run time. (1) **The repository comes from the tracker contract.** `docs/agents/issue-tracker.md` § Addressing names it, every PR and tracker call names that repository explicitly, and **nothing derives one from a remote URL** — one remote has several spellings and a fork clone names two repositories, which is why the old `origin` derivation needed a `project.repo_ref` override and an ambiguity guard to correct itself. All three are deleted (#389). A node that finds the contract file missing STOPS and says so; it never falls back to a guess. No prompt or command doc may carry a host CLI token, subcommand or flag, or a provider name: it names a **role** and a **file**, and reads the current tool list of whatever server § Access names ([ADR-0016](docs/adr/0016-dlc-thin-process-layer.md)). A flag table frozen in a YAML file is stale the moment the tool changes, cannot be verified without a live tenant, and is copied as precedent by the next agent that reads it — a closed attempt shipped a subcommand that does not exist. **One carve-out, and it is narrow: a dated evidence citation may name a host.** A rule earned by a rejected call cannot be checked later without the run that earned it, so the date, the pull request and what the host did are the part worth keeping — the citation records what happened, and the instruction beside it stays generic, naming a role and a file. What stays forbidden is a payload, a subcommand or a flag written as something to send, and a date next to it changes nothing. Two citations of this shape are live in `unic-dlc-pr-review.yaml`: the anchor a host accepted on a file no revision touched, and the four coordinates it required of an inline thread (#407). Both sit under a generic rule that tells a node to ask the tracker. (2) **Explicit staging.** Every committing node stages a named list, one `git add <path>` per path, then confirms with `git status --porcelain`; never `git add -A`/`.`/`-u`, and never `pr-body.md`, `*.tmp.md`, `*.scratch.md`, or anything under `$ARTIFACTS_DIR` (Archon's per-run dir, outside the repo tree). `/build`'s `build-state.json` is committed **once**, at `open-pr` — never in a loop iteration — because it is the durable proof of [ADR-0012](docs/adr/0012-fresh-context-red-green-separation.md)'s anti-cheat claim. Both rules are enforced by reading, across every Box YAML this Plugin ships, each Box's operator doc under `docs/boxes/` (they moved out of `.archon/commands/` in #294), and every command doc. Read them when you touch a Box, and again in review — a repository derived from a remote URL and a `git add -A` are both visible on the page.
- **A Box is read where it runs, so every reference in one resolves in the Consumer.** `/setup` copies the four Box YAMLs into a Consumer's `.archon/workflows/`, so a repo-relative path inside a Box is read against the **Consumer's** root and never this Plugin's. Most references are therefore correct as bare paths, and that is the majority on purpose — the tracker contract, the config, the installed Methods, and anything a node reads about the repository under review all mean the Consumer's own file. **Do not enumerate them here.** A list of what the Boxes reference is a mirror of the Boxes, nothing checks it, and the first draft of this bullet had already dropped `.archon/unic-dlc.config.yaml` despite eleven uses across the four — which is the failure mode the one-dependency-list rule above exists to prevent. The test is the question, not a list: **does this path name something the Consumer has?** A reference that means **this Plugin's** tree has to name the Plugin — "the `unic-archon-dlc` Plugin's own `README.md` § Dependencies" — because a bare `README.md` resolves in both trees and to the wrong document in one of them, which is harder to notice than a path resolving nowhere: the pointer it replaced said `lib/methods-manifest.mjs`, a file no Consumer has, and the rewrite traded a dangling pointer for a plausible one (#401). A bare `ADR-NNNN` in a Box always means a Plugin ADR, and this sentence is the whole of that convention. Be clear about what it buys and what it does not. A Consumer keeps a `docs/adr/` of its own, so the two numberings share a namespace — and `/build` is what grows the Consumer's: `unic-dlc-build.yaml`'s report node drafts `docs/adr/NNNN-<slug>.md` there. So a collision is scheduled rather than hypothetical, even though none exists today (`DXP-DesignSystem` holds `0001` and `0002`; the Boxes cite `0011` upward). This convention is what a reader lands on when one arrives, and it was chosen over rewriting every citation in the four Boxes because a citation carrying its own repository is a sentence nobody keeps current. **If the maintainer would rather have the citations qualified, that is a decision this bullet does not get to make for him** (#401).
- **Container follows structural need.** Archon workflows only for AFK-isolated, no-live-conversation work (`/build`, `/qa`, `/pr-review`, `/explore`); Claude Code commands/skills for interactive or repo-global work, composing Matt's originals. See [ADR-0017](docs/adr/0017-container-follows-structural-need.md).
- **No code at all.** This Plugin ships prose, four Box YAMLs and the Method Bundle. [ADR-0018](docs/adr/0018-generic-core-config-compose.md) drew a line between tested code and config-plus-composition and expected `lib/` to shrink to a deterministic core; it shrank to nothing (#381, amending that ADR), because an installed Plugin cannot resolve a module or an external package — `$CLAUDE_PLUGIN_ROOT` is unset inside the Bash tool and there is no `node_modules` ([ADR-0023](docs/adr/0023-build-generic-red-green-refactor-loop.md) §5, amended). A command reads config, the tracker contract and its Methods with its own tools; an Archon `script:` node inlines its logic. **Do not reintroduce a module** — not for schema validation, not for a topological sort, and above all not so that prose becomes testable, which the root `AGENTS.md` names as a defect rather than rigour.
- **A Plugin ADR takes its form from the `domain-modeling` Method, with two local rules.** Every Plugin ADR carries a `Status` line, and a decision that still stands while a detail of it changes is revised **inline** — the body edited to read as current, the status line gaining the revision date, no amendment block added — while a superseding ADR is reserved for a decision that is reversed or replaced; the shape, the Status set and the reasoning are in [`docs/adr/README.md`](docs/adr/README.md) (#452).
- **Session is scoped by Slug.** Every Session artefact (Findings, PRD, Issues JSON, `build-state.json`, report) is keyed by a single Slug under `<artifacts_dir>/<slug>/`. No cross-Session bleed. See [CONTEXT.md](CONTEXT.md).
- **The issue tracker is the single source of truth for "where are we."** `HANDOFF.md` and `ROADMAP.md` are dropped, and the old state-snapshot `triage` workflow is retired — no workflow writes either file. Per-thread continuity is handled by `/handoff` — one of Matt's skills, referenced in prose here and never implemented in this Plugin (it compacts the live conversation, so it cannot be an Archon workflow — see [ADR-0017](docs/adr/0017-container-follows-structural-need.md)), which writes a throwaway file, not a durable repo snapshot. See [ADR-0013](docs/adr/0013-tracker-single-source-of-truth.md).
- **The tracker contract is two repo-local prose files, not a config schema.** `docs/agents/issue-tracker.md` carries **Access** (which MCP server or skill serves this tracker), **Addressing** (the repository) and **Work-item scope** (the one filter every search applies); `docs/agents/triage-labels.md` carries the seventeen canonical roles, each row naming its value **and** the **axis** that carries it. `/unic-archon-dlc:setup` owns both, and `setup-matt-pocock-skills` must never run over them — it writes another host's template over the first and reverts the second to a five-role `wontfix` vocabulary. **The axis belongs to the role, not to the tier**: measured on a real tenant, **five of the eight** state roles cannot be states at all — writing a state while work is open moves an already-active item backwards on the board, so only the three terminal roles are states there and the five open-work roles are tags. So `.archon/unic-dlc.config.yaml` holds **no tracker facts** — the `tracker` block, `classification.labels` and `project.pr_strategy` are gone and `MANDATORY_PATHS` is `project.branching` alone (#389). A section earns its place in those two files only when it states a fact about this tenant: a server discovers its own API, so writing operations down freezes a flag table in Markdown, the same defect ADR-0016 forbids in a prompt and harder to notice. See [ADR-0024](docs/adr/0024-triage-intake-on-ramp.md), amended 2026-08-18.
- **`/triage` is the intake on-ramp — a thin wrapper over Matt's method, bound to the tracker contract.** It turns raw work (bugs, requests, QA findings, external PRs) into agent-ready tracker items feeding `/tickets`. It **composes Matt's `triage` method and reads the same two `docs/agents/` files the method reads** — the rule that once forbade that read is dead, because the two-writer problem it solved is now solved by removing one writer. `setup-matt-pocock-skills` is still **not** a Plugin dependency — only Matt's skill _methods_ are. It writes only to the tracker + `<triage.out_of_scope_dir>` (human present → no PR gate); it produces no `issues.json`/PRD. See [ADR-0024](docs/adr/0024-triage-intake-on-ramp.md).
- **The transition table: every point the Harness writes a Canonical role, and which one.** Stated here because it is Harness policy — the lifecycle is the _what_, so which role each Box writes is ours, not a tenant fact and not a Method's procedure. It is written down as a whole because the two holes below were invisible while it was scattered, and because "before you write a role" is uncheckable without a list of the places that do.

  | Box          | at                     | role written                                                              |
  | ------------ | ---------------------- | ------------------------------------------------------------------------- |
  | `/triage`    | the outcome is agreed  | the agreed state role                                                     |
  | `/specs`     | —                      | none. The `to-spec` Method's publish step is overridden; `/tickets` files |
  | `/tickets`   | each item is published | `ready-for-agent`, plus a type and a priority role                        |
  | `/build`     | the PR opens           | **none, on purpose** — see below                                          |
  | `/pr-review` | the review posts       | none. The review is advisory; the merge gate is `/qa`                     |
  | `/qa`        | UAT is rejected        | `bug` + `ready-for-agent` on each finding                                 |
  | `/qa`        | the PR merges          | `resolved` on every item the PR links                                     |

  **`/build` writes no role, and needs none.** "An agent has started this" is already on the item: `open-pr` links each work item to the pull request, and every host surfaces that link on the item itself. So no `in-progress` Canonical role is needed — adding one would change the protocol every Box shares to duplicate a signal the host already gives. Recorded so nobody re-derives it.

  **A `state`, `type` or `priority` role is single-valued.** Only one role of a tier is true of an item at a time. Before a Box writes such a role it reads the other rows of that tier in `docs/agents/triage-labels.md` and retracts every one whose axis **holds many** values; an axis that holds one value retracts the old value itself. Every surface in the table above states this rule inline, because a Box node imports nothing ([ADR-0023](docs/adr/0023-build-generic-red-green-refactor-loop.md) §5). The rule reads the `holds` column and **never an axis name**: `Tag` and `Label` are host words, and a rule phrased on one is wrong on the next host — the same defect [ADR-0016](docs/adr/0016-dlc-thin-process-layer.md) forbids in a prompt, one level up. Before #389 every state role resolved to a single-value field, so nothing could accumulate and this rule had nothing to do; the moment a tenant puts a state role on a multi-value axis it becomes load-bearing.

  **An extra row in `triage-labels.md` changes no Box.** A Box names its roles literally — `/tickets` writes `ready-for-agent` — so a team-added role is inert, and that is by design: the Canonical roles are the protocol the Boxes share ([`CONTEXT.md`](CONTEXT.md)). The team owns each role's value, its axis and its cardinality; it never owns the role set. A team that wants a Box to behave differently forks the Method, because a transition is procedure, not a parameter.

- **The `## unic-archon-dlc` block in a Consumer's `CLAUDE.md` enumerates no Box and no pipeline stage.** Setup replaces the whole block delimited by `<!-- unic-archon-dlc:begin -->` and `<!-- unic-archon-dlc:end -->` in place, markers included, and preserves everything outside it verbatim across re-runs. A Box list and a pipeline order are what a Plugin release renames, reorders and drops with no Consumer-side change — `/archon-upgrade` fell out of the old block and nobody noticed — so the block carries only paths on the Consumer's own disk (`.archon/unic-dlc.config.yaml`, the tracker contract at `docs/agents/issue-tracker.md` and `docs/agents/triage-labels.md`, `.archon/workflows/` and its `unic-dlc-*.yaml` naming, and `.archon/methods/` — `.archon/methods.local/` left the block with the override tier it advertised, #381), `archon workflow list` and `archon workflow run <name> "<slug>"` to discover and run what is actually installed there, and a link to this Plugin's README for what each Box does. The contract pair earns its line because the block is a Consumer's only pointer to the two files a Box refuses to run without, and because those two are tenant-owned: the block says nothing regenerates them once they exist (#383). It names `/unic-archon-dlc:setup` alone, because it cannot say what regenerates it without naming it. Nothing detects a hand-edit between the markers and nothing will, so the block never presents itself as a managed document and carries no `AUTO-GENERATED — DO NOT EDIT` banner (#296).
- **Slopcheck before build.** Every new package referenced in `package.json` is verified against the npm registry before any RED/GREEN phase runs. Packages that fail are flagged `[ASSUMED]` and require explicit human approval.
- **Nyquist map gates the build.** Every issue in Issues JSON must carry a `test_command` (or `test_command_planned`) before `/build` consumes it — the gate runs in `/tickets` ([ADR-0022](docs/adr/0022-tickets-slice-to-build.md)); `/build` reads the build-ready `issues.json` directly ([ADR-0023](docs/adr/0023-build-generic-red-green-refactor-loop.md)).
- **The evidence gate is a deterministic writer's presence check, never a self-judging prompt.** `/build` declares `evidence_policy: { required: true }`; `verification` and `goals-check` report a boolean `passed` alongside their existing prose verdicts, and `verification` adds a three-state `test_outcome` — `pass`, `fail` or `unresolved` — because a check that could not run is not a green one, and `test` is the one need this gate cannot advance without (#430); a dedicated `evidence` script node deletes any stale file left by a prior resumed attempt, prints its own three-state verdict as JSON (a `script:` node has no `output_format`, so only stdout resolves downstream), then writes `$ARTIFACTS_DIR/evidence.json` only when both booleans are true and the test outcome is `pass`, mirroring it to `<artifacts_dir>/<slug>/evidence.json` so `open-pr` can stage it. `always_run: true` on `slopcheck`, `verification`, `goals-check`, `evidence` (and on `/qa`'s `verify-pr-base`, `e2e`, `coverage-gate`) opts each out of Archon's resume cache, because their exit code reports a fact about external or mutable state, not about itself — the same hole that let a resumed `/qa` run merge against a since-retargeted PR base. See [ADR-0033](docs/adr/0033-archon-070-schema-target.md) and [ADR-0034](docs/adr/0034-evidence-gate-deterministic-writer.md).
- **`/qa` gates on `gates.qa` and fail-closes the merge.** The QA Archon pipeline (e2e → coverage → UAT → verify-pr-base → merge) has two `approval:` gates (UAT + merge), both HITL by default and skipped in AFK; downstream nodes use `trigger_rule: all_done` so AFK auto-merges a clean build, while the merge node's fail-closed `when` blocks auto-merging a red e2e/coverage or a wrong PR base. `/qa` is also an **issue-producing on-ramp**: a UAT rejection files each defect directly as a `ready-for-agent` tracker item (through the tracker contract in `docs/agents/`, the inlined finding-capture brief shape — upstream's own `qa` Method was deprecated at v1.1.0 with no replacement (#281) — and the AI disclaimer) that feeds `/tickets` — it does not just halt. Never `lib/tracker-adapter.mjs` (dissolved). See [ADR-0025](docs/adr/0025-qa-pipeline-onramp.md).
- **`/pr-review` is a self-contained fan-out Archon review that harvests, never depends.** The PR-review Archon pipeline (bootstrap → guard → prep → review → synthesize → reconcile → review-gate → post) reviews the open PR and posts one summary discussion on the pull request itself plus per-line discussions, through the tracker its contract names — a host carries the first as a thread with no file anchored to it or as a comment on the PR, and the Box asks which rather than promising either. It **harvests `unic-pr-review`'s review learnings** (confidence→severity rubric, structured summary, hidden-marker idempotency, conditional spawn table, two-surface posting) with **no ADO code and no runtime dependency** on that plugin. `prep` composes **one Intent Brief** (linked work items + Confluence/MD docs + PR description + `PRD.md`) that is **injected into both review axes** (the quality lever) and surfaces cross-source contradictions. The single `review` node reads the `code-review` Method and runs **its own** two-axis sub-agent fan-out — Standards (repo standards + the twelve-item Fowler smell baseline, pasted in full because the sub-agent has no other access to it) and Spec (AC coverage, scope creep, wrong-looking implementations) — replacing seven hand-written aspect prompts (#281, ADR-0026 §8). Refactoring lives in that Standards axis, having left `/build`'s loop. This Box holds the **only review-posting authority**: `/build`'s `implement-review-precheck` runs the same Method as a local pre-check that posts nothing. Re-review is first-class — a dedicated `reconcile` node keyed on the `<!-- unic-dlc-pr-review:iteration=N -->` marker (never author identity) classifies findings new / still-present / fixed / regressed. The `review-gate` confirms before posting `when gates.pr-review == hitl` (AFK posts directly); posting is advisory — the real merge gate is `/qa`. Never `lib/tracker-adapter.mjs` (dissolved). See [ADR-0026](docs/adr/0026-pr-review-generic-archon-harvest.md).
- **`/improve-architecture` is a skill that composes Matt's method and owns ADR superseding.** The off-line, on-demand arch-health box is a **command/skill** (its core is a design grilling loop that needs the live conversation — [ADR-0017](docs/adr/0017-container-follows-structural-need.md)), not an Archon workflow. It **composes `improve-codebase-architecture` verbatim** (technical drift + deepening HTML report + `/grilling` loop, with `/codebase-design` vocabulary + `/domain-modeling`) and **earns its place** ([ADR-0021](docs/adr/0021-earns-its-place-compose-verbatim.md)) by adding three DLC layers the raw skill lacks: an **intent-drift** pass (PRD stories/ACs vs shipped), a **durable `arch-review.md`** artifact under `<artifacts_dir>/` ([ADR-0015](docs/adr/0015-workflows-slug-artifact-home.md)), and an **ADR-consolidation gate with superseding**. Two modes: `<slug>` → intent-grounded against that build session; no-arg → repo-wide sweep (dated artifact, intent-drift skipped). Superseding works across **both ADR homes** (plugin-local + repo-root), never deletes an ADR (old status → `Superseded by ADR-NNNN`, index updated in the matching `README.md`). Config load is **lenient** (off-line, touches no tracker); **no new config key** and no auto-hook (PLAN #8). It does **not** touch the legacy `unic-dlc-cleanup.yaml` — that is `/cleanup`'s (step 11) scope. See [ADR-0027](docs/adr/0027-improve-architecture-skill-superseding.md).
- **`/cleanup` is the repo-global operational janitor — a report-first command, not an Archon workflow.** It prunes the debris a lifecycle accumulates: merged/stale worktrees, stale branches/PRs, and stale `<artifacts_dir>/<slug>/` dirs. It **composes** Archon's own `archon isolation list` / `archon isolation cleanup [days] [--merged] [--include-closed]` / `archon complete <branch>` for worktree/branch lifecycle and the tracker `docs/agents/issue-tracker.md` § Access names, for PR/branch state — never a `tracker-adapter` lib (dissolved). It is a **command** because it mutates sibling worktrees/branches/PRs and so cannot run inside an isolated worktree ([ADR-0017](docs/adr/0017-container-follows-structural-need.md)). It **defaults to a report-only dry-run and never auto-deletes**: pruning needs `--apply` plus an explicit **per-category** confirmation, and `cleanup.dry_run: true` (the shipped default) keeps even `--apply` in report mode until overridden. A slug dir is prunable **only if** its PR/branch is merged or closed (`cleanup.prune_slug_dirs` defaults `false`); slug-dir pruning skips any dir containing a `LICENSE` (repo policy). It reads the new `cleanup` config block (`stale_days`/`dry_run`/`prune_slug_dirs`); config load is lenient (off-line). This step **retired** the legacy `unic-dlc-cleanup.yaml` + command stub, whose arch-review + ADR-consolidation content moved to `/improve-architecture` ([ADR-0027](docs/adr/0027-improve-architecture-skill-superseding.md)). See [ADR-0028](docs/adr/0028-cleanup-operational-janitor.md).
- **`/archon-upgrade` reports what a new Archon release means for this Plugin, and writes nothing in the repository it assesses.** A **command**, not a workflow: it needs the live conversation to ask which repository to read release notes from when discovery fails, and to put a decision table in front of a human ([ADR-0017](docs/adr/0017-container-follows-structural-need.md)). It compares the installed `archon` against the `0.7.0` floor stated in the command and stops when they match; discovers Archon's own upstream repository at run time from `brew`, and **asks rather than guesses** when that fails, so no Archon URL is hardcoded anywhere; reads the release notes for the range through `gh` and classifies each notable change **ADOPT / DEFER / VERIFY-ONLY / BREAKS-US**, naming the affected file and node and one next step per row. Two classifications are locked and **cited, never re-derived** — `workflow:` sub-runs are DEFER per [ADR-0033](docs/adr/0033-archon-070-schema-target.md) § Sub-runs, and Archon's own remote-resolution algorithm is VERIFY-ONLY, never BREAKS-US, per that ADR's § "Repository derivation": a recorded, deliberate divergence re-raised as a defect would relitigate a settled decision on every run. A **separate mandatory sub-pass** reads the notes for changed, removed and deprecated **defaults** against the Boxes' own node bodies, because both real 0.7.0 defects were an upstream default a Box still assumed, invisible to a new-field scan. The [ADR-0011](docs/adr/0011-archon-schema-target.md) trap re-assertion runs unconditionally: the command reads each installed `.archon/workflows/unic-dlc-*.yaml` and checks the four conventions itself, and a file it cannot read is a FAIL, never a silent PASS. Nothing else guards those conventions, so this read is the only place they are re-asserted. A **second unconditional step probes the Archon config keys this Plugin depends on**: it gives each key a distinctive value in a throwaway git repository outside every clone, runs a one-node Archon workflow there, and reads the verdict out of Archon's own output — **READ — value `<x>`**, **NOT READ**, or **INCONCLUSIVE**. NOT READ is the silent failure it exists for; a committed top-level `baseBranch:` in this monorepo was inert for weeks against an Archon that reads a nested path (#396). The keys live in **one table**, inside that step, and the prose says the path is Archon's to change — the method is behavioural because grepping the binary proves a string is present, not that anything reads it. That throwaway repository is the one thing the command writes, and it deletes it afterwards. `allowed-tools` carries `Read` and `Glob` beside `Bash` — the command reads files — and no `Write`: adoption stays a human decision recorded by hand. See [ADR-0035](docs/adr/0035-archon-upgrade-report.md).
- **`/explore` is the off-line, optional research + AFK-spike on-ramp — an Archon workflow whose `findings.md` is the `/specs` baton.** Never required; a precursor to `/specs` (PLAN #3/#8). The pipeline (bootstrap → guard → four parallel research nodes, each reading the `research` Method for its primary-source citation discipline (#281) → synthesize → spike → spike-ticket → spike-branch-gate → preserve-spike) writes `<artifacts_dir>/<slug>/findings.md`, where the **Integrated Brief** carries three explicitly-named lenses — **Domain Model / Established Decisions / Prior Research** — that `/specs`' load-context reads verbatim (the tightened handoff contract). The `spike` node is **AFK** (build/measure where feasible, else reason → VALIDATED/INVALIDATED/PARTIAL verdicts); **interactive prototyping stays Matt's `/prototype` skill**, referenced but never invoked (nodes have no live conversation — [ADR-0017](docs/adr/0017-container-follows-structural-need.md)). The `spike-branch-gate` is a config-gated `approval:` node (`gates.explore`, HITL default): APPROVE preserves the spike on `spike/<slug>`, AFK skips it (worktree left for `/cleanup`); the **spike ticket is filed before the gate** (through the tracker contract in `docs/agents/`, never a `tracker-adapter`/`labels-config` lib) so the durable output survives a discard. Every node is a self-contained prompt node — no plugin-`lib/` import ([ADR-0023](docs/adr/0023-build-generic-red-green-refactor-loop.md) §5); this step dissolved `findings-writer` + `spike-verdicts` and added no config key. See [ADR-0029](docs/adr/0029-explore-research-spike-onramp.md).
- **This monorepo is not a Consumer.** `/unic-archon-dlc:setup` must never run against it. An earlier dogfooding run left generated artefacts under `docs/agents/` and a marker-delimited block in the root `AGENTS.md`, which collided with `setup-matt-pocock-skills` over the same paths — the collision this Plugin's own `/triage` doctrine forbids. Both were removed and `docs/agents/*.md` is now hand-owned by the repo; Matt's skills are its only agent-skill driver. Test the Plugin against a scratch Consumer clone instead. See [root ADR-0033](../../../docs/adr/0033-de-dogfood-unic-archon-dlc.md).

## External dependencies

- **A project-scoped MCP server in the Consumer's `.mcp.json` reaches a Box.** Every Box that composes "the server § Access names" depends on this, and nothing had tested it until 2026-08-18: an Archon run under `~/.archon/workspaces/<org>/<repo>/worktrees/…` loaded the Consumer's registered tracker server and read work items, pull requests and threads. Project scope travels with the worktree, so a node gets the access an interactive session gets — at a path no human approved. A **personal**-scope server does not travel, which is why `/setup` tells a team to register theirs at project scope.
- **Archon workflow engine, version ≥ 0.7.0** (the 0.x line churns fast — 0.3.12 → 0.5.0 → 0.7.0 across weeks; the node schema is the stable contract, not the release number), present in the Consumer project. Setup verifies the version floor before writing any artefacts. A Box needs no git remote: the repository is a fact in `docs/agents/issue-tracker.md`, never something read off the checkout. Workflows follow the key-discriminated node schema plus `evidence_policy`/`always_run` — see [ADR-0011](docs/adr/0011-archon-schema-target.md) and [ADR-0033](docs/adr/0033-archon-070-schema-target.md).

## Do not add

- **Parallel-runner support before the linear path is operational.** The current happy path runs one Session at a time. Until that is rock-solid in real Consumers, do not add parallel-Session orchestration.
- **Per-plugin variants of the Slug scheme.** Slug is monorepo-wide vocabulary; do not introduce a Plugin-specific Slug format.
- **Consumer-side opt-out flags for individual boxes.** Until a real Consumer asks with a concrete use case, the box set ships as one bundle. See [ADR-0014](docs/adr/0014-workflow-per-box-decomposition.md).
- **Hardcoded tracker/tenant/OS specifics — or any `lib/` at all.** Read config and compose (MCP-first, CLI-fallback). A module cannot resolve where this Plugin runs, so reintroducing one ships a command that halts at Step 1; that is not a style preference, it is the defect #381 fixed. See [ADR-0016](docs/adr/0016-dlc-thin-process-layer.md) / [ADR-0018](docs/adr/0018-generic-core-config-compose.md) / [ADR-0023](docs/adr/0023-build-generic-red-green-refactor-loop.md) §5.
- **`HANDOFF.md` / `ROADMAP.md` revival, or any workflow that writes durable repo-state snapshots.** The tracker is the single source of truth. See [ADR-0013](docs/adr/0013-tracker-single-source-of-truth.md).
