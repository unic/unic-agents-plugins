# 0034. The evidence gate is a deterministic script writer, never a self-judging prompt

**Status:** Accepted (2026-08-10, revised 2026-10-28)

## Context

Archon 0.7.0's `evidence_policy: { required: true }` ([ADR-0033](0033-archon-070-schema-target.md)) refuses terminal `completed` unless `evidence.json` exists in the run's `$ARTIFACTS_DIR` — but the engine checks presence only. Whatever writes that file **is** the gate, in the same sense [ADR-0012](0012-fresh-context-red-green-separation.md) already identified for red/green: a check that can grade its own homework is not a check.

An AI prompt node that both judges the build (reads `verification`/`goals-check` output, decides pass/fail) and writes `evidence.json` accordingly would be exactly that: a prompt that judges itself green and then certifies itself green, with nothing external constraining the two decisions to agree. This is the same failure mode the slopcheck gate and [ADR-0012](0012-fresh-context-red-green-separation.md)'s red/green isolation exist to prevent.

## Decision

A dedicated **script node**, `evidence`, is the only writer of `evidence.json`. It is deterministic code, not an AI judgment:

1. **Refuse a missing `$ARTIFACTS_DIR` loudly, before anything else.** The engine exports it to script nodes and this is the plugin's only read of it, so an absent value is a breach of the engine contract, not a red verdict — the node exits **non-zero** with a message naming the contract and the floor. The check tests falsiness rather than `undefined` because the empty-string case is the dangerous one: unset throws inside `join()`, but `join('', 'evidence.json')` returns a **relative** path and does not throw, so the node would log a successful write while the engine's presence gate read the real `$ARTIFACTS_DIR` and found nothing — a run failing closed with a success line in its log. Falling back to the Session dir is explicitly rejected: the gate reads only `$ARTIFACTS_DIR`, so a fallback would make that silent case permanent.
2. **Delete-first, both copies.** Remove any `$ARTIFACTS_DIR/evidence.json` **and** any mirrored `<artifacts_dir>/<slug>/evidence.json` left by a prior attempt before doing anything else — `$ARTIFACTS_DIR` is per-run but a resumed run reuses it ([ADR-0033](0033-archon-070-schema-target.md)), and the Session dir is reused too, so a stale file from a previous, since-superseded attempt would certify a tree that is no longer green. The mirror needs this more than the original: the engine's presence gate reads only the `$ARTIFACTS_DIR` copy, so deleting that copy alone would leave a stale mirror for the Session commit to stage and a reviewer to read after an attempt that failed before writing.
3. **Read, don't judge.** It reads what `verification`, `goals-check` and the pre-check already computed through their `output_format`, without re-running or re-interpreting anything. That is the `passed` boolean **and** the `failures` list, cross-checked, **and `verification`'s three-state `test_outcome`** ([ADR-0037](0037-config-declares-sdlc-needs.md)). The third state is why the two booleans are not enough on their own. A suite that could not run reports no failures, so on the booleans alone an absent result and a green result are the same fact. A `test_outcome` that is not `pass` is red here whatever the booleans say, and the node's own verdict, printed to stdout as JSON because a `script:` node has no `output_format`, carries the same three states. `passed` alone is a self-report from the same prompt that wrote `failures`, so a `passed: true` beside a non-empty `failures` array would otherwise certify a tree whose own certificate listed the failures. Both prompts define `failures` as blockers only, so a non-empty list is a red verdict whatever the boolean says. This is a cross-check, not independence. Only re-running the suite would give that, and [ADR-0023](0023-build-generic-red-green-refactor-loop.md) §5 rules it out.
   - **Read the pre-check as a gate input.** `implement-review-precheck` runs the `code-review` Method over the whole build. Beside its prose `findings` it emits `status` (`ran` or `blocked`), `blocked_reason`, `hard_findings` and `notes`. A hard finding is a breached documented standard, or an acceptance criterion that is missing or implemented wrong, with a citation. A judgement call is a note. `goals-check` counts that a test and an implementation exist for each criterion, so it marks a criterion `COVERED` that the pre-check has read and found wrong. Before this revision `evidence` read only `verification` and `goals-check`, and a run whose pre-check named a broken criterion still certified `pass`. Now any `hard_findings` entry makes the verdict `fail`. A `status` other than `ran`, `blocked` included, makes it `unresolved` when nothing else is `fail`. `status` and `hard_findings` are self-reported by a prompt, exactly as `passed` is for `verification` and `goals-check`, so this is the same cross-check, not independence. `evidence` treats a malformed entry as hard rather than dropping it. An entry with an empty `citation` or a `category` outside the enum still makes the verdict `fail`. A field that `evidence` cannot read gives a null status or no arrays, so the verdict is `unresolved` or worse. `evidence` writes the cause to stderr and to `precheck_read_error` in `evidence.json`, which is an empty string when every read worked. A read counts as failed when the variable is unset, does not parse, or gives the wrong type, such as a `status` other than `ran` or `blocked`, or a `hard_findings` or `notes` that is not an array. A `notes` value that is not an array keeps its text in `precheck_read_error`. Notes change no verdict. They reach `evidence.json` and the pull request description.
   - **The pre-check reaches the script through a `with:` binding, never through its source.** A node-output reference in a `script:` body substitutes raw into the source. A boolean or an array lands as a valid literal, but a string lands unquoted, and wrapping it in quotes breaks on the first quote inside it. The pre-check's strings are free text, and the blocked sentence for a missing merge-base holds single quotes. This node's `with:` binds only the four fields it reads, `status`, `blocked_reason`, `hard_findings` and `notes`, never `findings`. The engine hands each one to the script as an `INPUTS_PRECHECK_<FIELD>` environment variable. A string field arrives as its raw text, and an array field as JSON text. The script parses the arrays inside a `try`, so no pre-check text is ever parsed as code. So the prose `findings` never counts against the environment size limit. A script node's `with:` arrived in Archon 0.10.0 ([Archon CHANGELOG](https://github.com/coleam00/Archon/blob/main/CHANGELOG.md), 0.10.0), so `/build` needs Archon 0.10.0 or later.
4. **Write on every verdict.** The node writes `$ARTIFACTS_DIR/evidence.json` whatever the verdict, with the verdict, `test_outcome`, `unresolved_needs`, both failure arrays, and the pre-check's `precheck_status`, `precheck_blocked_reason`, `hard_findings`, `precheck_notes` and `precheck_read_error`, so the file the engine demands says what failed. It then mirrors the file to `<artifacts_dir>/<slug>/evidence.json` (the Session-artifact home, [ADR-0015](0015-workflows-slug-artifact-home.md)), because `$ARTIFACTS_DIR` resolves outside the repo tree and is gone once `/cleanup` prunes the worktree, so without the mirror the file is invisible to a reviewer and to the node that commits the Session artefacts. The verdict, not the file's presence, decides how the run ends. Only `pass` opens a pull request, and any other verdict cancels the run with the work pushed ([ADR-0040](0040-build-verdict-decides-the-pull-request.md)). The engine's presence check stays, as a backstop for `evidence` ending without writing.
5. **`always_run: true`.** Its own exit code is a write op, not a verdict about the tree; a resumed run must re-derive the verdict from the CURRENT `verification`, `goals-check` and pre-check output on every attempt, never trust that a file left by an earlier attempt describes the CURRENT tree.

**Rejected alternative: a prompt writes `evidence.json` when it judges itself green.** This was the first design considered and is recorded here specifically so it is not proposed again: it collapses judgment and certification into the same actor, the exact failure [ADR-0012](0012-fresh-context-red-green-separation.md) and the slopcheck gate exist to prevent for red/green and for dependency trust respectively. A script has no incentive to agree with itself; a prompt asked to both decide and attest does.

### Measured on Archon 0.12.1

Measured on 2026-10-28 with the Archon v0.12.1 release binary `archon-darwin-arm64` (commit `5f2b4841`), downloaded with `gh release download v0.12.1 --repo coleam00/Archon`, with its sha256 checked against `checksums.txt`. A wrapper set `ARCHON_HOME` to a scratch folder and ran the binary by its path, against a scratch repository outside every clone, with `--no-worktree`.

- A string field read in quotes, the shape `evidence` uses for `test_outcome`, fails on a pre-check string. With a `blocked_reason` that holds single quotes, the `script:` node failed with `Expected ";" but found "develop"`.
- A `with:` binding of one field arrives in `INPUTS_<NAME>`. A string field arrives as its raw text and an array field as JSON text. A `blocked_reason` and array entries holding single and double quotes, a backslash, a backtick, a newline, `${` and a literal `$BASE_BRANCH` arrived unchanged and unsubstituted, beside a 200 KB `findings` that was not bound.
- `evidence` itself, taken from the Box and fed by stub nodes, ended exit 0 and wrote `evidence.json` in each of these cases:
  - one hard finding gave `fail`;
  - a hard finding with an empty `citation` and the category `vibes` gave `fail`;
  - a blocked pre-check with the no-merge-base sentence gave `unresolved`, with the sentence intact;
  - the same sentence followed by a quote, a backslash, a backtick, `${` and a newline gave `unresolved`, with the text intact;
  - a `status` of `maybe` gave `unresolved`;
  - notes only gave `pass`, with the notes in the file;
  - a failing `verification` beside a blocked pre-check gave `fail`;
  - a `haiku` prompt node with the pre-check's `output_format`, told to report the no-merge-base block, gave `unresolved` with the sentence intact;
  - a `haiku` prompt node whose schema did not require the four fields, and which emitted only `findings`, gave `unresolved`. The missing string arrived empty and each missing array as empty text, and `precheck_read_error` named all three.
- A producer that printed prose in place of JSON did not reach `evidence`. Its field references raised `OutputRefError` before the node started, and the run ended `failed`. Binding the producer's whole output instead would reach the script, but it would also put the prose `findings` into the environment.
- The machine's Archon v0.10.1 delivered a `with:` binding the same way, also measured on 2026-10-28.

Two limits are not measured. A `with:` value is an environment variable, and Linux caps one at 128 KiB. Only the four bound fields count against that cap, never `findings`, so the cap is reached only by a `blocked_reason`, a `hard_findings` array or a `notes` array larger than 128 KiB. Then the node would not start and the run would end `failed`. A pre-check that ends without the structured output its schema requires fails as a node, so `evidence` does not run and the run ends `failed`, as before this revision.

## Consequences

- `verification` and `goals-check` in `unic-dlc-build.yaml` carry a boolean `output_format` (`passed`, `failures`) alongside their existing prose verdicts, and `verification` adds `test_outcome` and `unresolved_needs` — the prose stays for the human at `build-pr-gate`; those fields are what the `evidence` node reads, and the engine's gate then checks only that `evidence` wrote the file.
- The `evidence` node depends on both and on `implement-review-precheck`, and runs after them, before `report`. `report.md` already folds in `$verification.output` and `$goals-check.output` verbatim. It now also leads section 2 with the number of pre-check hard findings, read from `evidence.json`.
- `implement-review-precheck` carries `status`, `blocked_reason`, `hard_findings` and `notes` in its `output_format` beside `findings`. Its prompt states which finding is hard and which is a note.
- No other Box gains an evidence gate in this ADR. `/qa`, `/pr-review`, and `/explore` have their own verdict-reporting nodes (`e2e`, `coverage-gate`, `uat-prep`, …) but none currently reaches a terminal `completed` state whose evidence needs this exact deterministic-writer shape; extending the pattern there is a separate decision.
